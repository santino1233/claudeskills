**PURPOSE (stated by user 2026-08-04) — this is the core design intent:** the boards are a **Claude-facing, app-scoped work queue**. Each board corresponds to an app; cards are the user's ideas/features/bugs. The point is that a future Claude session can open a board and know *which app/codebase/server* to act on, so the user can fire ideas into the right board and have Claude run through them against the correct app. Build FOR this: keep board → App → Server resolvable so Claude can go from "working the Soul Pilates board" → the bound Server (IP + platform-stored SSH creds via `decryptSecret(server.rootPasswordEnc)`) → do the work. A natural next enhancement is a per-App "working context" (code path on the box, repo, stack, build/deploy steps) so Claude doesn't re-discover each time.

**WORKFLOW RULE (user, 2026-08-04 — non-negotiable):** When Claude works through a board, it MUST keep the board a living record — **move the card along the pipeline** (Ideas → In progress when you START → Review or Done when finished) AND **post comments on the card** documenting decisions and the outcome (live URL, follow-ups) AS you work, not silently. Mechanics: `db.card.update({columnId, position})` + `db.cardComment.create({cardId, authorName:"Claude", body})`, or the `moveCard`/`addComment` server actions. The user noticed when a whole build shipped with the cards left untouched in Ideas — don't repeat that.
