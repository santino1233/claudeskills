# Brief: bm-ops (bare metal backend, admin, policy, health)
Read `/root/agent-notes/bm-release/CONTEXT.md` first. Worktree: `git -C /opt/nxeon worktree add /tank/dev-worktrees/bm-ops -b feature/bm-ops main`. Notes to `/root/agent-notes/bm-release/ops/`.

Do an honest end-to-end audit AND fix what you find. Answer each owner question with evidence (a table in your report: question, answer, how you verified, status).

1. **Auto deployment and auto pay.** Trace order to delivery: quote, wallet or card payment, our order record, the supplier order, payment capture ordering (never order before paid; never lose money paid for an order that fails; idempotency on retries and double-clicks), provisioning polling, OS install, delivery, credentials/IP reaching the customer, and renewal (auto-pay from wallet then card, failure handling, grace, suspension, termination). Exercise every branch against the mock and Stripe test mode with tests (extend `test/dedicated-order*.test.ts`). Find and fix bugs (partial failure, stuck orders, stale quotes, price drift between quote and charge, stock disappearing mid-checkout).
2. **IP purchases.** How does buying extra IPs work end to end (the IP order flow, `DedicatedIp`/`DedicatedIpOrder`, pricing, assignment to the server, reverse DNS, firewall/virtual MAC if applicable)? Does it work in the mock? Is it equivalent to what the supplier's own panel can do (list the panel's IP features vs ours and mark gaps)? Fix gaps that are in scope; list the rest.
3. **Parity with using the supplier panel.** Compare what a customer can do in our dashboard (power/reboot, rescue, reinstall, IPs, rDNS, monitoring, network, KVM/IPMI, backups/storage, boot options, DDoS settings) with the supplier's panel capabilities; produce a gap table with severity; implement the safest high-value gaps if small, otherwise write them up.
4. **No refunds, no discounts for dedicated servers (hard business rule).** Enforce it in CODE, not just copy: (a) no coupon, promo, partner/creator sitewide discount, referral credit, first-month-free, grandfather price, term discount or any other price reduction may apply to a dedicated order or renewal (find every discount mechanism with `grep` and prove each is excluded, with tests); (b) no refund path may touch a dedicated order: block customer-facing "money-back" copy and flows (check `MoneyBackNote` and any "30-day guarantee" text on dedicated surfaces), block admin refund tools on dedicated invoices/orders with a clear message (admin can still correct billing errors through an explicit, audited, separate mechanism: propose it, do not widen refunds), cancellation means the server runs to the end of the paid period with no proration or refund, and chargeback handling is documented. Add an explicit non-refundable acknowledgement requirement to the order (`acceptedNoRefundAt` recorded on the order; the wizard agent shows the checkbox, you enforce it server-side). Update ToS/terms text that is in the repo. Flag (do not decide): whether signup wallet credit / promo wallet credit may pay for a dedicated server (it is a discount in effect) and recommend.
5. **Admin portal management.** Review `app/admin/dedicated/*`: what can staff do today (see orders, servers, stock/catalogue sync, pricing rules, pin popular builds, regions, per-server actions)? Build what is missing for safe operation: an orders queue with states and stuck-order alerts, per-server detail with the supplier references (admin-only, names the supplier is fine), manual actions that are audited (retry a failed provisioning step, refresh server state from the supplier, mark delivered, send credentials again), renewal/billing view, health panel (catalogue sync age, mock/live flag, failed jobs), and an audit log. Everything role-gated like the other admin areas.
6. **Caching: customers must never wait on a supplier API call to render their dashboard.** Audit every customer-facing read path: the server dashboard, My Services rows, power state, IP lists, network, metrics. They must render from our DB/cache instantly, refreshed by worker jobs and by explicit refresh actions with sensible TTLs, with a visible "last updated" and graceful behaviour when the supplier is slow or down (stale data shown, never a spinner-forever or 500). Fix any path that calls the supplier during page render; add a cache layer where missing (DB-backed snapshot with `fetchedAt`, per-server refresh job, single-flight so concurrent viewers trigger one refresh). Measure render time with the supplier mock made artificially slow (e.g. 8 s) and show before/after.
7. **Health before public release.** Produce `/root/agent-notes/bm-release/ops/RELEASE-CHECKLIST.md`: every function that must be verified on a real server before the public flag is flipped (a short list the owner can run), plus monitoring and alerting gaps (failed jobs, stuck orders, supplier errors, price/stock sync failures) and what you fixed. Do NOT flip any public flag.
8. **Tracking data for the wizard agent.** Ensure the order/server record exposes what the wizard's tracking needs without a supplier call at render: status, step, `orderedAt`, expected delivery window (derive from the catalogue's stock/availability code such as 1H/24H/72H and from actual historical order-to-delivery durations in `DedicatedServer` once enough data exists), datacenter label (customer-facing name, never the supplier's), and the supplier task state when available (cached). Coordinate through `lib/dedicated/tracking.ts` types: read the wizard agent's branch `feature/bm-wizard` if it has committed them; otherwise define `lib/dedicated/tracking-data.ts` for your side and note it.

Tests, `devhost tsc` clean, screenshots of the admin screens (dark and light), the evidence table, and a list of anything that needs the real supplier account to verify.
