# Brief: bm-wizard (the dedicated deploy wizard)
Read `/root/agent-notes/bm-release/CONTEXT.md` first. Worktree: `git -C /opt/nxeon worktree add /tank/dev-worktrees/bm-wizard -b feature/bm-wizard main`. Notes to `/root/agent-notes/bm-release/wizard/`.

The wizard is `components/dedicated/flow/` (BareMetalFlow, Configurator, review and pay steps, the paid/provisioning state) at `/dashboard/dedicated?build=...`. Read the current screenshots first (`/root/agent-notes/bare-metal/jpg/04-configure-dark-desktop.jpg`, `07-pay-card-filled-test-mode-dark-desktop.jpg`) and the portal's own visual language (My Services cards, the deploy wizard for VPS at `/dashboard/deploy`, `btn-deploy`, `grad-text`, rim tokens). The wizard must look like the rest of the portal (navy surfaces, the owner's size renders from `lib/dedicated/size-tier.ts`, glass tags), not like a separate product.

Do:
1. **A nice but simple hero** at the top of the wizard (configure, review and pay): the build name with its size render (`buildArt`), the key specs as the icon mini-cards used in the catalogue, the chosen location with its flag, and a step indicator (Configure, Review, Pay). Calm, specific, not bloated.
2. **Fix the configure, review and pay sections.** Audit them for real problems (confusing layout, unclear option pricing, missing totals, price breakdown that does not explain setup fees/IPs/OS/storage, poor mobile layout, validation and error states, back-navigation losing choices, the card form and wallet choice, double-submit protection, a price that changes silently). Redesign what is weak, keep what works. Show a clear, itemised price summary that updates live, with the monthly price, the one-time setup fee and "due today".
3. **The classic deploy button.** Replace the action button on review/pay with the portal's classic `btn-deploy` ("Deploy server ->") everywhere in the wizard's final steps, with proper disabled/loading/success states.
4. **No refunds, no discounts, stated clearly.** On review/pay show a plain notice ("Dedicated servers are non-refundable and not eligible for discounts or promo codes") and an **acknowledgement checkbox** that must be ticked before the Deploy button works; send `acceptedNoRefund: true` to the order action. The bm-ops agent enforces it server-side and records it; if their branch is not merged yet, add the field to the client payload and note the contract in your report. Remove any coupon/promo input, "money-back" text or discount messaging from the dedicated flow.
5. **Deploying animation with order tracking.** After paying, replace the plain pending state with a proper tracking experience: an animated, restrained visual (the owner's size render with a slow assembling/powering-up feel, no tacky particles; respect reduced motion) and a step tracker: Order received, Payment confirmed, "Someone at our {location} data center is setting up your dedicated server", Installing your operating system, Ready (with credentials/IP), each with a state and time. Pull the real state when the data exists (status/step from the cached order record; supplier task state when the ops agent exposes it) and otherwise show an **estimated wait** ("Typically ready within about N hours") derived from real data: the catalogue availability code (1H/24H/72H) and historical order-to-delivery durations. Put the pure logic in `lib/dedicated/tracking.ts` (status + timestamps + availability code + history -> steps, progress and ETA text), with unit tests. Customer-facing wording must never name the supplier; use "our {Montreal} data center" (the customer-facing location label). The page polls the cached order record (not the supplier) every 20 to 30 s while active, shows "Last updated", and switches to the server dashboard link when delivered. Also surface the same tracker on the server's own page and My Services card while it is not yet delivered.
6. Phone layout, light theme, empty/error/loading states, keyboard accessibility.
