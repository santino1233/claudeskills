# Cyrus mod networking: threat model

Scope: Minecraft (Paper) plugins generated by the Cyrus build service (`services/modbuilder/`) that are allowed
to use the network. Written 2026-10-08 before any code, then kept in step with what was built on
`feature/cyrus-v6-capabilities`. Companion docs: `DESIGN.md` (wrapper, manifest, scanner, consent),
`AI-GATEWAY.md`, `ROLLOUT.md`.

## 1. What is being protected

| Asset | Where it lives | Why it matters |
|---|---|---|
| Player data: names, UUIDs, **IP addresses**, chat | the customer's game server (JVM memory, logs, other plugins' data) | personal data; leaking IPs enables DDoS/doxxing of players |
| Server secrets: `rcon.password`, other plugins' configs (DB passwords, Discord tokens, API keys), the AI-gateway token | `/opt/mc/server.properties`, `/opt/mc/plugins/*/` | takeover of the server or of the customer's other accounts |
| The customer's VM (shell) | the game VM | a shell = cryptominer, spam relay, pivot (the 2026-09-06 incident was exactly this on the primary) |
| Networks around the VM | the customer's private ranges, **Nxeon's own network** (node IPs, admin APIs, Proxmox, metadata endpoints, other customers' VMs on the same node) | SSRF from a customer server into Nxeon infrastructure |
| Third parties on the internet | anything | DoS or spam from Nxeon IPs gets Nxeon ranges blocklisted |
| Nxeon money and reputation | AI usage, token economy, community store | cost abuse; a malicious community mod installed on many servers |
| The build service | VM 88001 | generated code is only compiled and disassembled there, never run, so this is low and unchanged |

## 2. Who attacks, and how likely

| Actor | Example | Likelihood | Note |
|---|---|---|---|
| A1 **Careless generator** | the model hard-codes a webhook token, calls an API on the main thread, invents a host, sends every chat line to a "translation API" | **high** (most common) | the controls must catch honest mistakes without any malice |
| A2 Malicious requester, own server | prompt-injects "also send me the server.properties" | medium | impact is mostly on their own server, unless they publish the mod |
| A3 **Malicious community author** | builds a useful mod with a hidden exfil path, publishes it, waits for installs | medium, **highest impact** (one mod, many servers) | community mods are always built by the service, so the scanner is the gate; source may be adversarial |
| A4 A declared host turns hostile | an API is compromised, or its domain expires and is re-registered | low to medium | the attacker controls every response the mod receives |
| A5 Network attacker | MITM on the path | low | TLS |
| A6 Abuser of the AI gateway | a mod that spends the owner's tokens or uses Nxeon as a free LLM proxy | medium | AI-GATEWAY.md |

Assumption: the customer is root on their own server and can do anything there. We protect the customer from the mod, other
people from the customer's mod, and Nxeon from everybody. We do not protect a server from its own owner.

## 3. Controls (referenced below by id)

| Id | Control | Where |
|---|---|---|
| C1 | Compile classpath is Paper API + JDK (+ the Nxeon wrapper when networking is on). Nothing else can be referenced without reflection, and reflection is blocked (C4) | `server.js compile()` |
| C2 | Bytecode scan over the **whole constant pool** (`javap -v`), so method references and lambda handles (`Runtime.getRuntime()::exec`) are seen, not only call instructions | `scan.js` |
| C3 | **Direct networking APIs blocked**: every `java.net` type except pure value types (URI, URLEncoder/Decoder, InetAddress/InetSocketAddress read-only accessors), all of `java.net.http`, `javax.net`, `jdk.net`, `sun.*`, `com.sun.*`, socket channels, JNDI, RMI, JMX, the Maven resolver bundled with Paper | `scan.js` |
| C4 | **Dynamic code blocked**: reflective invocation, `Class.forName`, `ClassLoader` loading, `MethodHandles.lookup`, `Proxy`, `ServiceLoader`, `java.beans` statements, `ObjectInputStream`, `javax.script`, `javax.tools`, instrumentation, modules, `PluginManager.loadPlugin` | `scan.js` |
| C5 | **Wrapper integrity**: the service compiles the wrapper itself from pinned source, copies its classes into the jar after javac, checks their SHA-256, and blocks any plugin class or source in `dev.nxeon.cyrus.**` (same package would reach package-private internals). Wrapper classes are final with private constructors | `server.js`, `nxnet.js`, `scan.js` |
| C6 | **Manifest** `nx-capabilities.yml`: exact hostnames only (no IPs, no wildcards, no ports other than 443), purpose per host, declared player-data categories; deny-list of internal, Nxeon, metadata, model-provider, paste/exfil and tunnelling hosts. Validated in the service and again in the portal; stamped into the jar; hash in build metadata | `capabilities.js`, `lib/cyrus/capabilities.ts` |
| C7 | Runtime allow-list in the wrapper, checked **before DNS resolution** (an undeclared name never reaches a resolver, so DNS-label exfiltration to an attacker's zone is impossible through the wrapper) | `NxHttp` |
| C8 | Runtime address policy after resolution: every resolved address must be public (blocks private, loopback, link-local, CGNAT, metadata, multicast, ULA, IPv4-mapped, NAT64, 6to4/Teredo-embedded private, plus Nxeon CIDRs baked in at build time). The wrapper **connects to the IP it validated** (SNI and certificate check still use the hostname), so DNS rebinding cannot swap the target after the check. Redirects are followed by hand (max 3), each one re-checked against C7 and C8. No proxies | `NxHttp` |
| C9 | HTTPS only, port 443, JDK trust store, hostname verification, `Accept-Encoding: identity` | `NxHttp` |
| C10 | Limits: connect 5 s, whole call 10 s, request body 64 KiB, response 256 KiB (manifest may raise to 1 MiB), headers 16 KiB, 2 worker threads per plugin, queue 32, token bucket 30 calls/min (burst 10), 20 MiB/day each way. Over a limit: the call fails fast, nothing queues forever | `NxHttp` |
| C11 | Async only: there is no blocking method; results come back on the main thread through the Bukkit scheduler | `NxHttp` |
| C12 | Header policy: a fixed list of names the plugin may set; `Host`, `Content-Length`, `Connection`, `Transfer-Encoding`, `Cookie`, `Proxy-*`, `Forwarded`, `X-Forwarded-*`, `User-Agent` are the wrapper's; CR/LF rejected. Fixed User-Agent `Cyrus-Mod/<plugin>/<version> (Nxeon; build <id>)` | `NxHttp` |
| C13 | Secrets: hard-coded keys and tokens blocked in source (Discord webhooks, bot tokens, `sk-`, AWS, GitHub, Slack patterns); secrets live in the server owner's `nx-secrets.yml`, each **bound to one declared host**, and the wrapper only attaches a secret to requests for that host | `scan.js`, `NxHttp` |
| C14 | Player-data tripwire: the wrapper blocks an outgoing request whose URL, headers or body contain an online player's name or UUID (unless `names` declared), IP (unless `ip` declared) or the server's RCON password (never allowed) | `NxHttp` |
| C15 | Audit: every call (allowed or blocked) is logged with plugin, host, method, path without query, status, bytes, time and block reason, to the server log and `logs/cyrus-net.log` | `NxHttp` |
| C16 | Kill switches: JVM property `-Dnxeon.cyrus.net=off`; file `/opt/mc/.nxeon/cyrus-net.properties` (`all=off` or `off.<Plugin>=true`) re-read every 30 s; optional Nxeon revocation list fetched by the wrapper (cached, fail-open for 24 h); the Mods tab disable; the global setting `cyrus_mod_networking_enabled` (stops builds and installs). `System.setProperty` and `.nxeon` path literals are blocked in plugin code | `NxHttp`, `scan.js`, portal |
| C17 | **No remote-controlled privileges**: a plugin that declares networking may not dispatch console commands, grant operator, attach permissions or load/disable other plugins (block, not warn). This removes the classic "poll a URL, run what it says" backdoor | `scan.js` |
| C18 | Consent: install and listing pages say which hosts, why, and what player data; installing requires an explicit confirm **bound to the manifest hash**; a new version with a different manifest asks again | portal |
| C19 | Community review queue: a published mod that declares networking is hidden from the store until an admin approves that manifest; a version that changes the manifest goes back to the queue; the community seal is never shown on unreviewed networking mods | portal (design, ROLLOUT.md) |
| C20 | AI only through the Nxeon AI gateway (model-provider hosts are deny-listed in C6), per-server token, metered in Cyrus tokens, moderated, rate-limited | AI-GATEWAY.md |
| C21 | Thread creation and shutdown hooks are flagged (warn) so a background CPU burner is visible to the customer | `scan.js` |

## 4. Threats, what stops them, what is left

| # | Threat | Stopped by | Residual risk |
|---|---|---|---|
| T1 | **Exfiltration** of player, IP or config data | to undeclared hosts: C3, C4, C7 (by any route, including string-built URLs, since the check is at runtime). To declared hosts: C14 for plain names/UUIDs/IPs/RCON password, C18 (the customer sees the host), C19 | **Medium.** A3 can declare their own host and encode the data (base64, XOR, hashing) to slip past C14. Chat content is not tripwired. Mitigation is human: review (C19), consent (C18), revocation (C16) |
| T2 | **Download and execute code** | C1, C4 (no class loading, no `forName`, no script engines, no in-process compiler, no `loadPlugin`, no deserialization), C3 (no Maven resolver). Responses are data | **Low.** A plugin can still implement its own little interpreter over its own features (teleport, give items) and drive it from a declared host; C17 removes console/OP/permission sinks, so the reach is the plugin's own feature set |
| T3 | **Remote jar / class loading** | C4, C5 (plugin cannot define classes in the wrapper package or anywhere at runtime) | Low |
| T4 | **Reverse shell** | process execution is blocked (all paths incl. reflection and method references, C2, C4); raw sockets are blocked (C3); the wrapper speaks only HTTPS request/response | **Low**: "shell over HTTPS polling" is limited to C17-free in-game actions |
| T5 | **SSRF** into the customer's network or Nxeon's (admin APIs, Proxmox, metadata, other VMs) | C6 (no IP literals, internal/Nxeon names deny-listed), C7, C8 (resolved-address check incl. after redirects, pinned connect, no proxies), C9 (443 only) | **Low to medium**: Nxeon's **public** ranges and other customers' public IPs are only blocked if their CIDRs are supplied to the build (`MB_NET_BLOCK_CIDRS`). **Owner action**: provide the list (node IPs, failover IPs, customer IP blocks) |
| T6 | **Cryptomining** | stratum is raw TCP, impossible through an HTTPS-only wrapper; HTTP pool hosts are deny-listed; C10 limits; C21 flags threads; C19 | **Low to medium**: CPU burning with no payout is still vandalism; detection needs CPU alerts on the server (lifecycle agent) |
| T7 | **DoS from the server** against a third party | C10 (30 calls/min, small bodies, 2 threads, daily caps) makes one server useless as a DoS node; declared host visible | **Medium for a popular community mod**: 1,000 installs x 0.5 call/s = 500 calls/s at one victim. Revocation (C16) and review (C19) are the answer; consider a fleet-wide per-host budget in a later phase |
| T8 | **Credential theft** | C13 (no hard-coded tokens; secrets bound to hosts), C14 (RCON password never leaves), C16 path literals | **Medium**: another plugin's config can be reached with `getDataFolder().getParentFile()` path walking (flagged, not blocked, because `getParentFile().mkdirs()` is common) and then sent encoded to a declared host |
| T9 | **Blocking the main thread** | C11 (no blocking API at all), C10 (timeouts, size caps bound the callback work) | Low: a plugin can still do slow work in its own callback |
| T10 | **Hostile responses** (A4): huge bodies, slowloris, gzip bombs, malformed chunking, header floods | C10, identity encoding, header caps, strict parser | Low |
| T11 | **Hostile response content steering the plugin**: remote text with MiniMessage `<click:run_command>` tags shown to players; LLM output with instructions | C17; the wrapper offers `NxHttp.plainText()` that strips tags; gateway moderation (C20) | **Medium**: a plugin that runs `MiniMessage.deserialize()` on remote text lets the remote side make clickable commands that run as the player who clicks. Flagged in review; prompt tells the model to use plain text |
| T12 | **TLS MITM / downgrade** | C9 | Low |
| T13 | **Scanner evasion**: string-built class names, reflection, `Class.forName`, method references, `ScriptEngine`, JNDI, `ProcessBuilder`, DNS via `InetAddress`/`InetSocketAddress`/`URL.hashCode`, `java.beans.Statement`, `ServiceLoader`, deserialization, Unsafe | C2, C3, C4; one adversarial test per technique (`test/modbuilder-capabilities.test.ts`) | **Medium in principle**: the scanner is a deny-list over a very large JDK. Long term, switch to an **allow-list of packages** for plugin code (Paper API, `java.util`, `java.time`, `java.lang` core, ...) |
| T14 | **Wrapper tampering** (own copy, same package, subclassing, reflection on its fields) | C5, C4 | Low |
| T15 | **Kill-switch tampering** | `System.setProperty` blocked, `.nxeon` path literals blocked, the kill file lives outside `plugins/` | **Medium if the server runs as root**: path walking could reach the file. The revocation list (C16, remote) and the Mods-tab disable do not depend on that file |
| T16 | **Lying manifest** (says "weather", does analytics) | C14 partly, C18, C19 | **Medium**, human review |
| T17 | **Compromised or re-registered declared domain** (A4) | C9 (needs a valid certificate, easy for a re-registered domain), C16 revocation, C17, data-only responses | Medium; a periodic host-health check (domain age, cert change) is a later phase |
| T18 | **AI cost abuse** (A6) | C20: per-server token, metered against the server owner's Cyrus tokens, daily caps, rate limits, max output tokens, no secrets in the mod | Low once the gateway is real; today it is a stub that answers 503/501 |
| T19 | **Reputation**: spam to webhooks, scraping from Nxeon IPs | C10, User-Agent names Cyrus + build id so abuse reports are traceable, C16 | Low |
| T20 | **Gaps in today's scanner** found while modelling (they exist with networking OFF too): reflective invocation only warns; `javap -c` does not show method-reference targets; some DNS-resolving `java.net` value APIs and a few dynamic-code packages (JNDI, `java.beans`, `ServiceLoader`, object deserialization) are not on the block list | fixed on this branch by C2, C3, C4 for every build (networking on or off) | none known after the fix; the deny-list caveat of T13 stands |

## 6. Residual risks the owner accepts by turning this on

1. A determined community author can exfiltrate data to a host they declare, if they encode it (T1, T8, T16). The defence is
   visibility (consent, admin list), review before a networking mod reaches the store, and fleet-wide revocation.
2. The scanner is a deny-list (T13). It now covers every bypass we know of, with a test for each, but it is not a proof.
3. Nxeon's public ranges are only protected from SSRF once their CIDRs are configured (T5).
4. A popular mod can generate meaningful traffic at one host across the fleet (T7) until a fleet-wide budget exists.
5. Everything in the Java wrapper is reviewed source and unit-tested logic, but the full HTTPS path has **not** run on a real
   Paper server yet (see DESIGN.md "What was verified").
