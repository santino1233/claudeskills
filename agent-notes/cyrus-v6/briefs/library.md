"Maybe create massive mod creation libraries with tons of trained, trialed and tested data that can be utilised for mod creation, whilst also keeping the mod generation cheap. Do you think it's worth it to train Cyrus on other pre-created mods?" Build a **verified pattern library** instead, used through retrieval into the cached prompt prefix.

## Your scope: the Cyrus Pattern Library (Minecraft first, generic schema)
1. **Policy first** (`LICENSING-POLICY.md`): which sources are allowed (permissively licensed example projects such as MIT/Apache/MIT-0 official examples, the platform docs' own samples where the licence permits, Nxeon-authored patterns, and Cyrus's OWN successful builds), which are not (anything all-rights-reserved or GPL being copied, bulk scraping Modrinth/CurseForge/Spigot/GitHub in violation of terms, community mods without the author's explicit opt-in). Verify each source's licence by reading it; record SPDX id, URL, commit and attribution requirements in the pattern metadata. For customer builds, design an **explicit opt-in** (listing setting) before a build can become a library pattern, plus removal on request.
2. **Schema** (`lib/cyrus/library/types.ts`, JSON next to the service like the knowledge packs so the Node service can read it): a pattern = id, title, category (the universal categories from `lib/cyrus/categories.ts`/routing agent), description, the code (small, focused: a command, config load/save, listener, scheduler task, GUI, economy hook, scoreboard, placeholders, database access...), dependencies, the **verification record** (game, version(s), loader, build/compile result, runtime load result, date, tool versions), source and licence, and a content hash. Patterns are distilled building blocks, not whole mods.
3. **Pipeline**: ingest from the allowed sources (start with the permissive examples and Paper API docs examples already in the repo/service sheets; mine the service's own passing evals under `services/modbuilder/eval`, read-only), normalise, **compile-verify each pattern against each supported version** with the service's toolchain (on node-2, Paper API jars are public: see how the service gets them; no proprietary files), and write the verification record. A scheduled re-verify script reruns the library against a new game version and flags patterns that stop compiling or loading, feeding the lifecycle agent's out-of-date logic (expose `lib/cyrus/library/status.ts`).
4. **Retrieval and cost**: design and implement how patterns reach the model cheaply: a compact pattern index in the cached prefix, the model asks for/gets only the patterns for the planned features (by category and feature tags, deterministic first), measured against **CloudAPIBench's warning that retrieval can hurt common APIs**: so run an A/B on the existing eval set (offline cost model unless you can run it safely; you may run at most 6 real builds in total, and only through a path that does not touch VM 88001's production role; otherwise report a design with predicted effects and say so). Report token and cost deltas and the first-try pass rate impact, honestly.
5. **Scale plan**: how to grow it from a few dozen patterns to thousands: contributor workflow, review and test gates, deduplication, per-version maintenance burden, storage and size limits, and a quality bar (a pattern must compile on every claimed version and load on a real Paper server in the harness before it is `verified`). Include the "learning loop": each successful, opted-in customer build proposes new patterns; failures update the failure rules (the knowledge packs the game agents are building in `GameSupport.knowledge`; align with their shape and the efficiency agent's `export-knowledge.js`).
6. Seed at least 25 verified Minecraft patterns you can fully justify licence-wise (Nxeon-authored ones are fine, written fresh by you and verified), with the tooling to add more. Do NOT deploy and do NOT touch VM 88001.

Finish with a short report: library size, verification coverage, measured or modelled effect on cost and quality, licensing decisions the owner must confirm, and what you recommend next.
