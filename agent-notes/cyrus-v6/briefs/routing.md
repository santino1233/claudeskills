## Your scope
**A. Broad-request prompt routing.** Today the dock needs a hovered game or mod. Make it understand free requests from anywhere (the core, a game, a mod, or nothing selected): "make me a mod for Minecraft where creepers drop diamonds", "work on my frost axe mod and fix the cooldown", "add a shop command to my Rust plugin", "what mods do I have for Valheim", "update the boss mod for the new version". Design `RouteDecision = { intent: create|refine|fix|explain|install|unknown, gameId, categoryId, projectId?, confidence, reason, clarify? }` in `lib/cyrus/route.ts`.
- **Cost-aware design (the owner wants lower API spend without a dumber product):** a deterministic fast path first (game aliases from the registry, "my <name> mod" fuzzy-matched against the user's own projects and mod titles, intent verbs, category keywords), costing zero API calls. Only genuinely ambiguous input may use ONE tiny structured classification call through the existing cheapest-model plumbing, or (better when cheap enough) show a one-tap clarification chip ("Frost Axe v2 or Frost Axe?"). The current selection/hover always wins as context.
- The UI response: the camera glides to the target node (existing `camera.ts`/`forge.ts` machinery), the branch lights up, the preview opens, the dock shows a chip ("Creating a new Minecraft mod in Weapons" / "Refining Frost Axe"). Unknown or unsupported game: say so plainly and offer supported games.
- Unit tests with 60+ varied phrases (typos, other word orders, multi-game ambiguity, "my mod" with 0/1/many matches). Keep it pure and client-safe so it can run in the dock instantly.

**B. Universal preset categories.** One canonical set, identical across all games (examples the owner gave: Environment, Weapons, Performance; design the final ~14 to 16 so they map cleanly onto the NxLabs mod store; read `lib/cyrus-mods/registry.ts`, the store pages and `lib/cyrus/categories.ts`). For each: id, label, one-line blurb, an **SVG icon** (24x24, `currentColor`, consistent stroke; reuse the existing 12 in `components/icons`/`CategoryIcons.tsx` and draw the missing ones), and per-game availability (a game's `GameSupport.categories` once the game agents land; until then a sensible default table). The **auto-sorter** classifies a finished mod into one primary + up to two secondary categories from the prompt, the generated code and the build metadata, deterministic signals first (zero API), with a cheap fallback only when confidence is low. Mod categories on the map become these presets; migrate existing projects (read-only DB access in dev; write a safe migration helper, do not run it on production).

**C. Listing dialog after a mod is built** (and "Edit listing" when clicking an existing mod): title, category (auto-selected, shows "auto-sorted", easy override), icon/logo (upload, or pick a generated/preset glyph, cropped to the rounded shape), brief description (AI draft from the build summary where free, editable, 280 chars). Define `lib/cyrus/listing.ts` NOW and commit it early: `ModListingInput = { title, categoryId, secondaryCategoryIds, iconAssetId|null, description }` plus validators. The **community agent owns storage** (`saveModListing(projectIdOrBuildId, input)` and the NxLabs page); call it through a thin adapter `lib/cyrus/listing-client.ts` that works with a local fallback until their branch is merged. Do not touch the NxLabs page.
