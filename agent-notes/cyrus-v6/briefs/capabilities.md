## Context: the owner's decision (2026-10-08)
The Minecraft build service's safety scan currently hard-blocks ALL networking. The owner said: "loosen. Maybe some networking is possible for the advancement of mod creation." This is the main ceiling on advanced mods (web APIs, Discord/webhook integrations, remote config, economy and voting services, AI-driven NPCs). Nxeon has had serious security incidents (a platform RCE, a cryptominer from a framework bug), so loosen **safely and by design, not by deleting the rule**.

## Your scope: a capability model for mod networking
1. **Threat model first** (`THREAT-MODEL.md`): what a malicious or careless generated plugin could do with network access (data exfiltration of player/IP/config data, downloading and executing code, class-loading remote jars, reverse shells, SSRF into the customer's own network or the Nxeon internal network, crypto mining, DoS from the server, credential theft, blocking the main thread), and which of those each control stops.
2. **Design**: mods may only use the network through a vetted Nxeon wrapper (`NxHttp`: a small, audited helper class the build service injects into every plugin's classpath/shade), never raw `java.net`, `HttpClient`, sockets, URLClassLoader or reflection around it. The wrapper enforces: HTTPS only, a **declared host allow-list in the plugin manifest** (`nx-capabilities.yml`: hosts, purpose, reads/writes player data yes/no), resolved-IP checks blocking private/loopback/link-local/metadata ranges (anti-SSRF, including after redirects and DNS rebinding), async only (never on the server thread), request/response size and time limits, rate limits, no custom headers that smuggle secrets, a User-Agent identifying Cyrus, logging of every outbound call, and a kill switch via config.
3. **Scanner changes** in the service (`scan.js`, `precheck.js`, rules): replace "block all networking" with "block direct networking APIs; allow only the wrapper with a manifest-declared allow-list"; keep blocking process execution, native loading, remote class loading, `Runtime.exec`, file access outside the plugin folder, reflection that reaches around the wrapper, obfuscation, and anything else already blocked. Add tests with adversarial examples (string-built URLs, reflection, `Class.forName`, ScriptEngine, JNDI, `ProcessBuilder`, DNS exfil via `InetAddress`).
4. **Customer consent and visibility**: the install flow (and the listing page, `Explain` data and NxLabs page) shows "This mod connects to: hosts, for: purposes, and can/cannot send player data"; installation requires an explicit confirm; the manifest is part of the build metadata (`MbFinding`/meta in `lib/modbuilder/types.ts`). Add the pure helpers in `lib/cyrus/capabilities.ts` (types, validation, summary text) and the UI hooks as small additive components (the lifecycle agent owns the install dialog: expose a `CapabilityConsent` component and tell them the contract).
5. **AI features without arbitrary networking (design, behind a flag)**: for LLM-driven NPCs or AI chat in mods, the plugin never talks to a model provider directly. It calls a **Nxeon AI gateway** endpoint (design the API: per-server token, metered in tokens through the existing economy, rate limits, moderation, prompt-injection and abuse controls, no secrets in the mod). Write the design and the minimal gateway stub; do not build the model plumbing.
6. **Roll-out plan**: phases, kill switches (per mod, per customer, global setting), admin visibility (which published mods declare networking), review queue for community mods that declare networking, and what the owner must approve before enabling (default OFF; a setting `cyrus_mod_networking_enabled`).
7. Do NOT deploy, do NOT touch VM 88001, and run no real outbound network from tests (use local fixtures). Deliver the patch to `services/modbuilder/` on your branch with install notes (next service version, rollback), unit tests and a clean `devhost tsc`.

Finish with a short report: the threat model's residual risks, what you recommend the owner approve, and an honest statement of what could only be verified against a real build.
