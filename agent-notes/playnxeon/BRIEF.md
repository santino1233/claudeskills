# Brief: move NEW game servers to `<name>.playnxeon.com` (existing servers stay exactly as they are)

## The owner's request (2026-10-08, verbatim)
> playnxeon.com is now ours. here is the cloudflare key for editing its dns zone
> I want to change the sub domain for all new game servers (including free Minecraft) to run on this domain *name*.playnxeon.com
> the playnxeon.com domain itself should forward to the game servers marketing page
> Currently they run like this *name*.play.nxeon.cloud
> We need to look at everything on how it runs on this and make a flawless migration to the new domain structure.
> Current game servers will stay the same as i dont want to disrupt their services

## What the coordinator already found
- Today ONE global setting `free_minecraft_domain` (default `play.nxeon.cloud`, read via `getSetting` in ~40 places: `lib/game-subdomain-dns.ts` `gameSubdomainBase()`, `lib/actions-free-minecraft.ts`, `lib/actions-server.ts`, the marketing pages, the deploy wizards, the directory, health checks, KB/AI-chat facts, emails, admin panels...) decides the domain for EVERY server. Rows (`Server.subdomain`, `FreeMinecraftServer.subdomain`) store only the short name. **Changing that setting would change every existing server's address at once.** So the design needs a **per-server domain** (a nullable column; NULL means the legacy `play.nxeon.cloud`), set only on servers created after the switch.
- DNS today: `*.play.nxeon.cloud` is a wildcard A record to node-2 (178.63.94.114, DNS-only) for the free tier (mc-router on the freemc-host VM routes by hostname); paid servers get exact A (and for Java an SRV `_minecraft._tcp.<host>`) records created by `lib/game-subdomain-dns.ts` using the platform token `CLOUDFLARE_DNS_API_TOKEN` against the `nxeon.cloud` zone; `worker/game-subdomain-sync.ts` keeps them in sync. Read all of it plus `lib/cloudflare-dns.ts`, `lib/game-subdomain*.ts`, `lib/game-connect.ts`, `worker/freemc-health.ts`, `scripts/freemc/**`, `docs/DOCUMENTATION.md` sections on free Minecraft and game subdomains.
- The new zone `playnxeon.com` (Cloudflare zone id `4e2410256fea9fa31163d6e7059a0991`) currently has `A playnxeon.com 2.57.91.91 (proxied)` and `CNAME www -> playnxeon.com (proxied)` (a placeholder from before; do not touch it, the coordinator will replace it at cutover). The new token can edit DNS but **cannot** create Cloudflare redirect/ruleset rules (Authentication error), so the root domain's forward must be done by our own web server: `playnxeon.com` and `www.playnxeon.com` -> 301 to the game servers marketing page (find its real route, probably `https://nxeon.cloud/game-servers`; the owner means "the game servers marketing page"). Game records must be DNS-only (grey cloud): Cloudflare does not proxy game TCP/UDP.

## The token (handle with care)
Stored in `/root/secrets/cloudflare-playnxeon.env` (mode 600, variable `CLOUDFLARE_API_TOKEN`). **Never print it, never commit it, never copy it to node-2 or any worktree, never paste it into docs or notes.** Production will read it from a NEW env var `CLOUDFLARE_PLAYNXEON_API_TOKEN` (name it exactly that); the owner/coordinator adds it to `/opt/nxeon/.env` (you must not edit any `.env`). Live Cloudflare calls: only from the PRIMARY with a tiny script (no builds there), and only (a) read-only GETs of the playnxeon.com zone, and (b) creating then immediately deleting ONE throwaway record named `zz-test-<random>.playnxeon.com` to prove the code path. **Never modify or delete any existing record, never touch the nxeon.cloud zone or any customer zone.** All other tests use a mocked fetch.
