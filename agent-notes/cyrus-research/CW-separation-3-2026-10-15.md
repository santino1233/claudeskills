Branch `feature/cyrus-separation3` (worktree /tank/dev-worktrees/cyrus-separation3, from main 89608a9f = rc16). NOT merged, NOT deployed, no behaviour change, no migration. Numbers below are generated by `scripts/cyrus/separation-report.ts` (rerun it; it is the source of truth).

## 0. The short answer for the owner
Cyrus is **seamed, not separate**. The engine (lib/cyrus, 735 files) is clean: 4 files import Nxeon, all of them client-safe shared kernel. The coupling that remains is not in the engine, it is in three places:
1. **UI and routes**: 437 Cyrus app/component files, 123 of them import Nxeon directly (lib/db 66, lib/auth 56, components/ui 34, lib/mods 29, lib/rate-limit 26). This is the bulk of the remaining work.
2. **One process, one DB, one config, one deploy**: same Next build, same nxeon-web unit, same Postgres schema (50 Cyrus tables in the Nxeon schema), same Setting table (137 cyrus_* keys), same env (251 CYRUS_* names), same worker. cyrus.my proxies to the Nxeon upstream.
3. **Two owner decisions are still open and block the last third**: who owns money (Stripe) and the SSO model.

Everything on the roadmap that does not need those decisions can ship now as flag-free, ratchet-protected steps (M1-M4 below).

## 2. Target architecture options

### A. Same repo, same process, hard module boundary + host adapter (today)
- What changes: nothing structural. Finish ratchets: reverse-import guard (done), UI->lib/db guard, route handlers use host.* only.
- Risks: boundary erodes by convention; the Cyrus UI keeps shipping with Nxeon deploys and an Nxeon outage is a Cyrus outage; cannot scale or restart independently; one Next build for ~8,300 files.
- Migration: none. Rollback: n/a.
- Deploys: unchanged (one promote, one blue/green); cyrus.my vhost unchanged; auth unchanged (bridge inside one app); cost: zero extra.
- Verdict: a safe floor, not an end state. It does not answer "separate app".

### B. Same repo, separate Next.js app and process (cyrus-web), own worker, shared Postgres with schema/role separation
- What changes: apps/cyrus (own next.config, layout, globals, middleware) importing lib/cyrus via a package alias; app/dashboard/cyrus, app/api/cyrus, app/cyrus-host, app/admin/cyrus*, app/(marketing)/mods/cyrus move to it; Nxeon keeps thin entry points (NxLabs cards, server banner, Stripe webhook hook) that call lib/cyrus-client. cyrus-web.service on its own port; cyrus-worker.service; Cyrus tables move to schema `cyrus` with role `cyrus_app` (no grants on Nxeon tables; Nxeon role loses Cyrus tables) in the same Postgres; own .env.
- Risks: the 123 UI files must stop importing lib/db/auth first (the real work); shared UI primitives need a package or a copy; two builds on node-2 (more build-lock contention); shared Postgres means a noisy neighbour is still possible; middleware split must be exact or cyrus.my 404s.
- Migration: see M1-M8. Rollback: nginx upstream flip back to nxeon_web (the old routes stay mounted but flagged until soak ends); DB schema move is `ALTER TABLE .. SET SCHEMA`, reversible in the same transaction; keep search_path fallback.
- Deploys: promote-cyrus.sh armed (already written: staging first, side-port smoke, atomic symlink, auto rollback, worker after web); a Cyrus-only change no longer restarts nxeon-web; Nxeon promote unchanged. cyrus.my vhost: change upstream to 127.0.0.1:<cyrus port>; admin host the same. Auth: bridge flows stay (cookie already separate), but Cyrus stops reading Nxeon's session table: it verifies the assertion and holds its own session row. Cost: one more Next process (~1-2 GB RSS), one more build slot; no new servers, no new DB.
- Verdict: recommended.

### C. Fully standalone product: own DB, OIDC SSO, Nxeon API client for installs/servers/billing
- What changes: B plus own database instance, own host(s) (plan says own VPS pair + build host behind Cloudflare), OIDC from Nxeon as IdP, host.http adapter only (already built), wallet charge via Nxeon API (or own Stripe), object storage/CDN, own monitoring and backups, own admin.
- Risks: data cutover with write freeze (28 to 50 tables, no FKs helps); Stripe customers/subscriptions live in Nxeon's account (split-brain on refunds, chargebacks); install state in ServerMod/GameMod needs an Nxeon-side install API contract hardened; region latency (primary Singapore, node-2 Germany); ops burden (2nd stack to patch, back up, monitor); legal (separate ToS/Privacy).
- Migration: B, then P5 data split rehearsal, P7 infra move. Rollback: repoint DNS + DB dump restore within the soak week (runbook CYRUS-MOVE-RUNBOOK.md). Deploys: independent pipeline fully; cyrus.my goes to its own origin; auth: pure OIDC/assertion, no shared session table; cost: new servers (~2 boxes), Cloudflare/R2, plus ongoing ops time.
- Verdict: a valid end state only if there is a business reason (sell/partner Cyrus, separate ops team, scale). Do not start here; B makes C a deployment exercise rather than a rewrite.

## 6. Owner decisions needed
1. **Billing owner**: Nxeon as the only payment provider (wallet debits via API; Cyrus never touches Stripe; recommended, already the coded default) vs Cyrus' own Stripe account (adapter built, split-brain risk on existing subscriptions/refunds). Blocks M-C and removes the 6 Stripe imports.
2. **SSO model**: Nxeon as IdP forever (recommended; assertion flow built, one account, one wallet) vs Cyrus own accounts at launch. Decides whether Cyrus keeps any session table of its own.
3. **Domain and cookies**: stay on cyrus.my with host-only `__Host-` cookies (current; users re-login once on cutover) and keep /mods/cyrus SEO via 301 or serve it from Cyrus; admin host (CYRUS_ADMIN_HOST) on its own name.
4. **Database**: same Postgres with own schema + role (M8, recommended next) vs own instance (C). Also own Anthropic credentials/budget vs shared.
5. **Process split**: approve the "B" direction (a separate cyrus-web process and worker on the same box) so M5-M8 can be scheduled as run-alone sessions.
6. Hosting for C (own VPS pair, region) and whether Cyrus is meant to be sold/partnered; if not, stop at B.
