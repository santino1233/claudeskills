# Cyrus full plan: separation, bridge, portals, infra, one-session updates (2026-10-11)
Companion to CYRUS-TRACKER.md (state) and MASTER-PLAN.md (engine). Estimates are my judgement, not measurements.

## 0. Target architecture (what "done" looks like)
```
 cyrus.my (landing, Cloudflare)      app.cyrus.my  (Cyrus customer app)      admin.cyrus.my (Cyrus admin)
                          \               |                    /
                           +---- Cyrus services: API (api.cyrus.my) + workers + own DB + object storage/CDN + build service
                                          |  ^
                    Cyrus -> Nxeon:       |  |   Nxeon -> Cyrus:
                    Nxeon Platform API    |  |   Cyrus API v1 + signed webhooks
                    (identity, wallet,    v  |   (projects, builds, mods, entitlements)
                     servers, files)   nxeon.cloud (portal, billing, game servers, admin)
```
Principles: (1) Nxeon = identity + money + game-server hosting; Cyrus = everything about mods. (2) One account, one wallet, one Stripe. (3) The browser talks straight to the service that owns the feature; no relaying. (4) Every cross-app call is a versioned, tested contract. (5) Nothing in Nxeon breaks at any step: each phase is flag-gated and reversible.

## 1. Decisions to lock first (my recommendation in bold)
1. Repo shape: **one monorepo, several deployables** (`apps/nxeon`, `apps/cyrus`, `apps/cyrus-admin`, `apps/cyrus-site`, `packages/*` shared). One Claude session edits one repo and ships only what changed. Separate repos would make "one update applies everywhere" a cross-repo chore.
2. Payment: **Nxeon wallet/Stripe is the only money system** (already the coded default). Cyrus sells nothing itself; it asks Nxeon to charge.
3. Identity: **Nxeon is the identity provider**; cyrus.my accounts are lazily provisioned Nxeon accounts. "Sign in with Cyrus" on Nxeon is a button that lands on the same account.
4. Server access: **per-server, scoped grants** (section 3.3), never SSH credentials.
5. Hosting for Cyrus services: own VPS/dedicated pair (app + build/worker) behind Cloudflare; **separate Postgres** from Nxeon. Region chosen deliberately (primary is Singapore, node-2 Germany).
6. Admin: **Cyrus has its own admin; Nxeon admin shows a read-only Cyrus summary + deep link**; staff identity and roles come from Nxeon rbac.
7. Terms: separate Cyrus ToS/Privacy (with the library licence grant), reviewed by a lawyer before public launch.

## 3. The bridge, in detail
### 3.1 Identity and account lifecycle
Stable subject id (Nxeon user id) everywhere; never match on email. Sign in with Nxeon on cyrus.my (OIDC-style redirect, state/nonce, signed assertion, own session cookie); "Sign in with Cyrus" on Nxeon goes to the same account. First visit provisions the Cyrus profile silently (no second signup). Gaps to cover: verified email required; MFA lives at Nxeon; per-host sessions + back-channel logout; account suspend/ban propagation both ways (Cyrus-only abuse flags a user at Nxeon); deletion + data export cascade (GDPR) across both; Cyrus ToS acceptance recorded per user with version; admin view-as across hosts without leaking; account merge when someone already has two identities.
### 3.2 Money, plans, tokens
Plans (Katara, Saka, Yakko) and token packs are products in Nxeon billing; entitlement is Nxeon's, mirrored into Cyrus by webhook + short-TTL cache, **fail closed** when unknown. Purchases started on either site go through Nxeon checkout; credit to Cyrus tokens is idempotent (outbox, retries, daily reconciliation, honest pending/failed states); refunds and chargebacks reverse credits; invoices/VAT stay in Nxeon. Gaps: Creator Partner Program attribution for Cyrus plans (50% first / 10% recurring exists at Nxeon: decide if it applies); promo codes; free-tier grants and abuse limits; spend caps per user and global (AI cost vs revenue dashboard); tax/VAT decision still open.
### 3.3 Connecting servers ("install straight onto my servers")
Connect = a consent screen at Nxeon listing exactly what Cyrus may do, per server the user ticks. Scopes: `servers.read` (id, name, game, version/loader, status, RAM/CPU, player count), `inventory.read` (installed plugins/mods with versions: feeds the conflict engine before every build/install), `files.write.mods` (only mods/plugins/config/datapack/resource-pack paths, with hash preconditions), `server.reload` / `server.restart` (budgeted), `logs.read.tail` (for Server Doctor, health, post-install checks), `pack.set` (resource-pack URL + hash). Cyrus keeps the delivery orchestrator (journal, rollback); Nxeon exposes safe primitives and audits every call. Revocable any time; every call tied to user + server + grant; rate limited; idempotent. Webhooks Nxeon -> Cyrus: `server.version_changed` (mark mods outdated), `server.deleted`, `server.restarted`, `grant.revoked`. Users without Nxeon servers: download jar, "Try it" throwaway server, install guide. Pull to improve results: target version from the server, RAM-aware warnings (worldgen, creatures), existing-plugin conflicts, "Create a mod for this server" button on every Nxeon server page that prefills Cyrus.
### 3.4 Cross-product experience
Shared header package (account menu, balance, notifications, product switcher); deep links with silent SSO; one notification system (build finished, install result, mod outdated, takedown) with one preference center, email through Nxeon's mail stack from a cyrus.my sender (SPF/DKIM/DMARC for the new domain); support: tickets stay in Nxeon, carry Cyrus context (build id, spec, flight record), support can view-as; unified status page; cross-domain analytics/attribution (Meta/Google conversions, referral cookies) and a cookie-consent banner; SEO: `/mods/cyrus` redirect strategy to cyrus.my.

## 4. Cyrus customer app (app.cyrus.my): what it needs
Dashboard (projects, recent builds, mods, plan + tokens, connected servers, library contributions, activity); project page (revisions, builds with Test Flight status, install/rollback, configs, studios: texture, sound, model, motion, designers, config); new-mod flow with game/version/server pickers and cost shown first; library browser; mod pages (public, pass-rate badges, ratings); account (profile, connected Nxeon account + servers + grants, personal Cyrus API keys, notification prefs, data export/delete); plans/tokens (buy via Nxeon); onboarding tour and templates gallery; docs/help; changelog (customer-facing only); teams/shared projects (later, a real gap); referral/creator pages.
## 5. Admin portal (admin.cyrus.my, staff via Nxeon roles)
Overview (queue depth, build success rate, spend vs revenue, errors); builds (search, logs, rerun, kill, cost); users (lookup, plan/tokens adjust with audit, view-as, ban/suspend, GDPR tools); library moderation (hold queue, takedown/DMCA log, near-duplicate tools, trademark/real-weapon lists); flags and kill switches (launch-pair guard, AI gateway kill, global build pause, per-feature off); evals and pass-rates (run, compare, publish); capacity (build VM, node-2 flights, meshgen jobs, storage); cost governance (per-model spend, per-user caps, alerts); audit log; announcements; reconciliation view (Nxeon wallet vs Cyrus tokens, webhook failures, replay). Nxeon admin gets a read-only Cyrus card + deep link.

## 6. Cloudflare and infrastructure
cyrus.my zone (pending): apex + www (landing static), app, api, admin, cdn/packs (R2) subdomains; WAF + rate limits, Turnstile on sign-up and "Create Mod", bot protection; Full (strict) with origin certs; static cache rules; pack and library delivery from R2/CDN with signed URLs (sound library only when cleared). Nxeon zones per P2 (client IP first, game and mail records stay grey). Own Postgres + PgBouncer, nightly encrypted backups off-box, second copy of the proprietary SFX library (tank is one disk with no redundancy). Staging environment; observability (logs, metrics, uptime, error tracking, per-build cost telemetry); status page; secrets in one place; **the build service must move from subscription login to an API key before any public launch** with hard spend caps; build-queue fairness and capacity plan beyond the single build VM.

## 7. One Claude session updates everything
Monorepo layout above. `scripts/ship <target|all>` detects what changed (apps and packages graph), runs tests + the seam ratchet + OpenAPI contract tests, builds on node-2 (never in the live tree), deploys through health-checked promote scripts with auto-rollback: nxeon (existing promote-production.sh), cyrus app + api + worker (`promote-cyrus.sh`), landing (rsync to /var/www/cyrus.my or Cloudflare Pages), admin. Shared packages guarantee "same behaviour" across nxeon.cloud, cyrus.my and the Nxeon tab; API contracts are versioned (v1 stays until v2 proven; expand/contract DB migrations; N and N-1 compatible) so deploy order never breaks anything; flags allow dark launches and instant rollback. Rule kept: never edit or build in /opt/nxeon; worktrees + devhost; deploy only through the promote scripts.
