# ED: Which other studios does Cyrus need for Minecraft? (2026-10-18)

Read-only research. Labels: **V** = verified in code/data this session, **U** = unverified (inference/memory). No secrets printed; production data summarised only.

## 0. Evidence base and its limits
- V: coverage matrix `lib/cyrus/adapters/minecraft-coverage.json` has **93** archetypes (not 85): 55 covered, 30 partial, 3 gap, 5 impossible. Lane counts: config 81, texture 10, designHud 7, designItem 7, designMenu 6, datapack 6, sound 5, designQuest 2, motion 2, designBoss/worldgen/creature/model3d/itemStates/library 1 each. So 81 of 93 archetypes are still built by "config + model-written Java" with no editor at all.
- V: studios that exist (docs/cyrus/03-studios.md, lib/cyrus/studios, designer/*): Texture, Sound, Model (3 layers), Motion panel, Item/Menu+Quest/Boss designers, HUD design spec, Config & Stats, Rooms card + Room Studio, Mod Packs/Import, Data pack screen (**read-only**), Library browser. Creature studio "not built (UI)"; Mob Skin gated "coming soon".
- V: datapack emitters exist ONLY for recipe, loot, advancement, enchantment (`lib/cyrus/datapack/emit/*`), plus worldgen. Recipe kinds: shaped, shapeless, 4 cooking kinds, stonecutting, smithing_transform. Loot kinds: generic, chest, entity, block, fishing, gift. The model writes these specs; the customer cannot edit them visually.
- V (production, read-only SELECT on ModBuild/CyrusProject): **119 builds, 33 projects (root builds), ONE user** (the owner/QA), 88 succeeded / 31 failed, 23 CyrusProjects. About 70 of the 119 builds are the Infinite Dungeon refine chain. So prompt "counts" below are **projects out of 33**, keyword-matched on prompt + changeRequest, and are owner-biased. They show direction, not market demand. No real customer prompts exist yet (V).
- V: market-demand proxy = BA corpus (173 Modrinth plugins, 141 datapacks, 43 resource packs) and BF catalogue (156 techniques: 38 covered, 41 partial, 77 missing).
- Project-level keyword counts (V, n=33): creature/mob 17, loot-or-drops 10, HUD/boss bar/action bar/scoreboard 9, chest 8, minigame/arena/dungeon 6, structure/room 5, shop/economy 4, sound 4, enchant 2, recipe 2, particle 2, menu/gui/shop 3, npc/dialogue 1, quest/advancement 1, skin 0, localisation 0. CyrusGuardRefusal has 6 rows (class only inspected).
- V (CK): where Cyrus struggled on the flagship mod: (a) refines silently reverted config defaults (max-floors 100 vs 11, config-version) twice; (b) creature wiring lost on refine (now guarded); (c) many "budget" failures when one prompt asked for themes + a boss (split into 3-5 smaller refines to pass); (d) floors are "generated block patterns", room content needs the structure lane; (e) bosses beyond one have only built-in ability enums (only Frost Colossus got bespoke abilities); (f) Test Flight is boot-only, nothing verified in game. Takeaway: the pain is **large free-form generation in one model call + no human-editable intermediate**. Studios that turn big code asks into small typed specs fix exactly that.

## 2. Top 5 to build next (ranked by value / effort / evidence)

Ranking logic: (a) the data pack screen is read-only while emitters are complete, so editors over finished engines are cheapest and make the output human-editable (fixes the CK "everything is one big model call" pain); (b) the owner's own prompts are dominated by mobs, loot, HUD, arenas; (c) corpus demand. Structure and Creature studios are already in flight and are not repeated here.

### 1) Loot & Crate Studio (value 5, effort M, V gap: no editor over a complete emitter)
Inputs: a source (mob type or custom creature from the project, block, vanilla chest/structure, fishing, or a crate), pools with rolls and bonus rolls, entries (item with count/functions, tag, nested table, empty), weights, conditions (random chance, looting, tool, biome, killed-by-player) and an optional "tier" scaler (floor/level to weight shift). Crate mode adds key item, preview odds menu and a server-side roll; opening animation as a later flag (matrix says "no animation"). Outputs: the existing datapack spec fragments (`kind: generic|chest|entity|block|fishing|gift`) plus, for crates, a small config block the golden `mc-crates` plugin path reads; saved as an `edited` revision exactly like the designers (3-way merge, human wins). Ships into the mod via the datapack lane (zip in the pack) or the crate config + generated plugin class; for custom-item results it references item ids from the Item Designer. Verification: schema + reference checks already in `datapack/spec.ts` (item/tag/table refs, own ids); an odds simulator (run the real weight/conditions code 10,000 times, show per-item rate and expected value, flag unreachable/zero-weight entries and value-per-roll vs a budget); Test Flight boot plus a server-side `/loot` roll probe via RCON (BF #13 pattern) on one version. Guardrail: real-money gambling refusal stays (BF #11).

### 2) Recipe & Progression Studio (recipes + advancements + custom enchants + trades) (value 4, effort M; V: emitters exist, no editor, tiny prompt count so ship as one studio)
Inputs: crafting-grid editor (3x3 drag/drop, shaped/shapeless, cooking time/xp, smithing 3-slot, stonecutting), result picker (vanilla or project item with name/lore/model), unlock method (recipe book, advancement); advancement tree canvas with parent links, icon, frame, triggers (the 7 existing), rewards (recipes, loot table, xp); enchantment form (levels, max, effects: value/post_attack/attribute, supported items); villager trade rows via the plugin Merchant path (no datapack lane on 1.21.x). Outputs: datapack spec (recipe, advancement, enchantment) and a trades config. Ships via the datapack lane per version (singular folder names, pack formats already in registry). Verification: existing `validate.ts` per-version re-validation, duplicate-recipe and ingredient-loop checks, "can I obtain every ingredient?" reachability check (an ingredient made only by itself is flagged), advancement graph cycle/orphan check, Test Flight boot and a `/recipe give` style RCON probe. Reuse the Data pack screen's per-version states and rollback banner (V in docs). Value is partly "unblocks Data pack screen from read-only".

### 3) Ability Library (shared action graphs for items, bosses, mobs) (value 4, effort M; V: Item Designer has the graph, CK shows other bosses limited to enum abilities, ability refines refused/failed)
Inputs: a named ability (trigger, conditions, cost/mana/cooldown, actions from the existing palette: shoot, beam, blast, dash, particles, sounds, summon, vein_break when flag on), parameters exposed to Config Studio. Outputs: `cyrus.ability.v1` spec referenced by id from item, boss phase, mob and quest reward specs (one compile path, the `DesignConfig` budget/runtime caps apply unchanged). Ships inside the generated plugin through the existing designer compiler (`compile.ts`, `java.ts`); no new runtime. Verification: designer `check` and `simulate`, 5 budget meters, per-activation budget warnings; golden for "ability used by item and boss"; crucially a **mechanical regression check** that an ability survives a refine (CK lesson: refines rewrote things). This turns the big "give my 10 bosses abilities" prompt into 10 small edits.

### 4) Arena & Minigame Studio (value 4, effort L; V: golden mc-arena exists, "arena reset is the weak spot", 6 of 33 projects mention minigame/arena/dungeon)
Phase 1 is a typed spec + form, not a canvas: pick a mode template (spleef, last-man-standing, parkour race, team deathmatch, wave survival, dungeon run), set lobby/countdown/min-max players/teams/scoring/rewards/respawn rules, link arenas from Structure Studio rooms (markers: spawn, exit, chest, objective), choose the reset strategy (disposable world per round, per BF #14, vs block snapshot restore). Outputs: `cyrus.minigame.v1` spec compiled to the arena golden's plugin scaffolding with config values exposed to Config Studio and HUD (scoreboard/boss bar) from designHud. Ships as plugin code + config. Verification: state-machine simulator in the browser (join, countdown, start, win), RCON bot flight in survival mode (BF #1: stress bot is creative today, so combat arenas can pass falsely), reset test (play, reset, diff block hash), and the 3 silent-failure checks from BF #14.

### 5) HUD & Font Skin Studio (upgrade of designHud to GUI sprites, menu backgrounds, tooltip frames) (value 3-4, effort M; V: 9 of 33 projects mention HUD/boss bar/action bar/scoreboard; 10 of 43 corpus packs use gui sprites; `HUD_EXCLUDE` refuses custom GUI textures)
Inputs: pick a vanilla UI element to skin (boss bar, hotbar, tooltip frame, container background), upload or generate a sprite (Texture Studio canvas), set glyph offsets/negative-space advances, preview over a mock screenshot at GUI scales 1-4. Outputs: resource-pack files (`textures/gui/sprites`, font providers, `tooltip_style` on 1.21.4+) in the existing pack builder, and menu designer `background` option. Ships in the server resource pack with the per-version pack format table; Bedrock raw-codepoint warning surfaced. Verification: pack validator per version, 3-scale preview render, real client screenshot (the `resourcePackClientVerified` flag stays false until a client check exists, U that it works on all four versions).

## 4. Not worth building as studios now
Localisation (0 prompts, no demand evidence), Player-skin NPC (needs packets; Mannequin only on 1.21.11), Biome/Dimension visual (engine-bound; jigsaw/custom dimensions are in stillCannot), Custom Block studio until the real-client look is verified, standalone Animation and Advancement studios (folded in above).

## 5. Caveats
- Prompt counts come from 33 projects by one user; treat the "Prompts" column as direction only (V). Substring noise ("minecraft" matches "craft") was removed in the final counts.
- Effort and value are my estimates (U). Gap sizes are V only where a file is named.
- I did not open the live Mob Skin or Structure Studio branches, so their completeness is U beyond the docs and git log.
- BF/BD/GAPS/BA were read at summary level (not every row); BD (modtools survey) was not re-read in full.
