## 1. How Cyrus and Nxeon fit together (the separation, plainly)
There are TWO directions of traffic. They are different jobs.

**A. Cyrus needs things FROM Nxeon** (sign-in, who the user is, wallet/payments, listing a user's game servers, writing files to a server and restarting it, notifications, settings/flags, audit log).
- This is the **host seam** (`lib/cyrus/host`): small interfaces Cyrus calls. Inside Nxeon, one file (`host/nxeon.ts`) answers them with the existing Nxeon code, unchanged. Moving Cyrus out means giving it a different answer to the same interfaces (an HTTP client that calls Nxeon's API instead).
- DONE: settings, rate limit, audit, auth, permissions, users/jobs/servers/installs, database access (97 Nxeon-table call sites to 0), worker schedule entry point, host paths/config. A test blocks any NEW direct Nxeon import.
- DONE 2026-10-11 (r34, `feature/cyrus-r34-separation2`): build engine (`host.builds`), mod pages (`host.mods`), money (`host.billing`: Stripe containment + wallet, default provider = Nxeon, own-Stripe adapter also built). Baseline **40 -> 5** imports, all client-safe/pure (rbac role table, net-policy JSON, token UI component, Terraria versions, mod-health rules): copied on move day. The app routes/pages/components still import Nxeon; those move with the UI.

**B. Nxeon needs things FROM Cyrus** (your idea: Cyrus is its own app and Nxeon feeds from its API: build status, a user's mods, the studios, library search, "install this mod").
- **Cyrus does NOT have its own external API today.** It has about 34 app routes inside the Nxeon app that its own screens use. There is no versioned, documented, token-authenticated API that another site could call.
- **STATUS 2026-10-11 (r34, NOT deployed, `CYRUS_API_V1` off):** phase 2 built: write endpoints (create project/build, request install + status, config values, library contribution) with idempotency keys, scopes, audit and the subject's access rule; webhooks Cyrus->Nxeon (5 events, signed, outbox + retries/dead letter, SQL proposed not run); Nxeon-side client + webhook receiver in `lib/cyrus-client` (no Cyrus imports); dual-mode proof (same conformance suite over the HTTP adapter against a local fake Nxeon, incl. wallet); move-day runbook `docs/CYRUS-MOVE-RUNBOOK.md`. Not built: mounting the host API in Nxeon, emitting webhooks from product code, Postgres stores. Report `AE-separation-api2.md`.
- **STATUS 2026-10-10 (r25, `feature/cyrus-r25-api`, NOT deployed, flag `CYRUS_API_V1` off):** design + route inventory (`cyrus-designs/v6-api/CYRUS-API-PLAN.md`), OpenAPI 3.1 contract generated from the Zod schemas (`docs/api/cyrus-v1.openapi.yaml`, 21 operations: 6 live, 15 planned; 5 webhooks planned), a read-only slice (health, projects list/get, builds get, catalog search/get; service tokens + scopes + rate limit + Ed25519 subject assertions; one real run on node-2), and the HTTP host adapter skeleton for direction A (`lib/cyrus/host/http.ts` + reference server, proven by one conformance suite on both transports). Not built: writes, webhooks sender/receiver, Nxeon client, the Nxeon-side mount. Report `V-api.md`.
- Original scope note: **Cyrus API v1**: an inventory of those routes turned into a versioned contract (OpenAPI), service-to-service auth plus user sign-in handoff (SSO), webhooks back to Nxeon (build finished, mod published, install result), and an Nxeon-side client. The Kodely partner pattern (SSO + Partner API, one account, one wallet) is the template; Cyrus would be the "partner" for direction A and expose an API for direction B.
- Recommended order: (1) finish seam A, (2) design Cyrus API v1 (a Sonnet audit + Opus design), (3) build the HTTP host adapter and the API, (4) run both modes side by side behind a flag, (5) move.

**Nothing breaks in the meantime:** inside Nxeon every host call delegates to the same code as before. Installs on customer servers, payments and your Nexion account work exactly as today.

**Move-day decisions (yours):** separate Stripe account vs Nxeon as the payment provider (wallet debits); SSO from Nxeon vs Cyrus's own accounts; new domain and cookie scope, and whether to keep `/mods/cyrus` SEO via redirects; where the Nxeon-side install API lives and how it authenticates; own database and Anthropic credentials vs shared. Top risks: Stripe customers/subscriptions live in Nxeon's account; balances must key off a stable subject id (never email); install records sit in Nxeon's `ServerMod`/`GameMod`; delivery uses SSH into customer VMs so an outside Cyrus needs a scoped Nxeon API, never credentials; hardcoded node-2 paths and credentials files (moved behind config, still to set).
