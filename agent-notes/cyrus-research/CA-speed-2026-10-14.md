Portal ModBuild (14 days): mean duration 59 s (10-08) up to 342 s (10-14, 13 builds, p50 304, p90 543, $0.82 mean), the owner's creature batch day.

What the numbers say:
- **Output tokens are the wall clock.** generate_ms = 3.5 + 9.0 s x (output tokens / 1000), correlation 0.989; multi-regression on (output k, turns): 9.5 s per 1k output tokens, turns add nothing (r2 0.98). ~108 tokens/s median. The 49.6k-token creature call (fox, 544 s, 9 turns, $0.91) is exactly that rate.
- **Most output tokens are thinking, not files.** Model-written file bytes / 3.3 vs billed output: plain 3.4k of 7.8k (57% thinking), sound 6.4k of 21.2k (70%), texture 6.6k of 26.0k (74%), designer 2.5k of 11.6k (78%), owner batch 7.4k of 28.7k (74%). Matches the stage events: "Planning" (everything before the first Write) is 65-75% of the generate call.
- **Time split of a build:** generate 91%, repairs 6%, guard 0.6%, compile+scan+design check 1.3%, queue wait 0 in the evals (in-flight 1). Test Flight adds a median 34 s (boot 19 s) after the jar exists, i.e. 40% on top of a plain build.
- **Turns:** 7.8 per generate, 6.6 Writes, 0.02 Reads. One Write per turn is common, but the per-turn overhead fits to about zero (batching writes saves nothing measurable). Max-turns is not a waste source (tail only).
- **Cache:** 85% of input tokens are cache reads, 15% cache writes, uncached ~0. First turn of a build reads the cached prefix 80% of the time (81% when the previous build was < 5 min ago, 82% at 5-60 min, cold only after > 1 h gaps). The prefix is ~28-37k tokens per call (system prompt is already lane-sliced: plain 16k, texture 17k, sound 18k, designer 21k, all lanes 34k tokens by the prompt builder + CLI tool schemas). Re-sent per call but read at 0.1x; cache TTL and prefix ordering are not the problem.
- **Cost:** generate 91% of $, repair calls 8.7%, guard 0.3%. 23% of builds needed at least one repair call.
- **Asset lanes are NOT parallel with code.** Texture/sound/creature/design specs are written by the same single generate call as the Java, in sequence (one process, one stream). Only after that do the deterministic rounds run (validate, autofix, pre-check, asset check, compile, scan; 2 s total). There is nothing to overlap there except the model call itself.
- **Repair rounds** add 6-25 s mean (designer 24 s, owner 22 s: boss-minions had 4 repair calls, $0.84 of $1.24, 238 s).

## 4. Safe rollout of the existing bank and recipes (not enabled)

What they do (code read): MB_STARTER_BANK=1 lets POST /builds carry `bank: {id, params}`; the service copies the Nxeon-authored golden entry, writes the params as settings defaults and runs the same non-AI gates (zero model calls; portal charges setting cyrus_tok_bank_charge=5 placeholder). 16 entries, compile+scan 64/64, Test Flight 16/16. Portal side needs CYRUS_STARTER_BANK. MB_RECIPES=1 selects <=2 verified recipes per FRESH build (rules + guard archetypes, never designer lane or change/import builds) and puts them in the first user turn; MB_RECIPES_HOLDBACK_PCT (default 20) deterministically skips injection by hash of build id, recorded as `recipes.{ids,holdback,injected}` on the record.

Plan: (1) recipes first, bank second (bank has ~0 matches today). (2) Recipes with holdback 20% for 3 days / >=40 plain+designer builds; compare injected vs holdback on pass@1, repairs, output tokens, seconds (eval-journal-stats). Ship if repairs/output tokens fall and pass@1 does not; raise holdback to 5%. (3) Bank only after the matcher shows >= 5% instant hits on real prompts; keep a 10% holdback by sending no `bank` for those. Rollback is one env var each.

## 5. Owner rollout recipe (nothing applied)

1. Merge/promote: `feature/cyrus-speed` is based on main f347f27a (rc12 chain). Merge into the next release branch, build image `modbuilder:0.18` with `TAG=modbuilder:0.18 bash scripts/cyrus/deploy-modbuilder.sh` when the service is idle (the owner batch is running now). With the new flags unset, the image behaves like 0.17 plus phaseChars.
2. Arm A (baseline): the same keys already exist in fourth1/fifth1 journals (plain 20 prompts s01..m12, texture tex-*, sound snd-*). Pick a 12-build subset: `--keys s01-heal,s05-join,m02-killstreak,m06-enchant,m10-growth,tex-gem-set,tex-food-pack,tex-config-hats,snd-shotgun-pump,snd-win-jingle,cov-warps,cov-sidebar`.
   `npx tsx scripts/cyrus/eval-run.ts --tag speedA --keys <list> --budget 6 --in-flight 1` (flag off; gives fresh numbers incl. phaseChars).
3. In /root/modbuilder.env on the VM set (one at a time, restart the container each time):
   - `MB_EFFORT_MAP=plain=low,designer=medium,texture=medium,sound=medium,default=high`
   - then separately `MB_FAST_HINT=1`
   Run arm B: `npx tsx scripts/cyrus/eval-run.ts --tag speedB --keys <same list> --budget 6 --in-flight 1`.
4. Compare with `npx tsx scripts/cyrus/eval-journal-stats.ts` (or report.md): seconds per lane, output tokens, `$`, pass@1, final pass, quality score, boot. Accept a lane when seconds drop >= 20% with pass@1 within 1 build of arm A and quality >= baseline; otherwise move that lane back to `high` (remove its entry).
5. Rollback: unset the var(s) in /root/modbuilder.env and restart the container (`TAG=modbuilder:0.17` to go back to the old image; the backup tgz is made by deploy-modbuilder.sh). No data migration.

## 6. Caveats

- The thinking share is an estimate from file bytes (3.3 bytes/token); phaseChars (new) replaces it with a measured split after the first builds on the new image.
- Effort has not been run on Sonnet 5.5 for quality here: that is exactly what step 2-4 measures. Plain/low is the safest first lane (85-93% first-try today, small outputs); texture/sound have the largest absolute saving but the weakest pass@1 (45-60%), so do them second.
- Eval timings are with in-flight 1 (no queue); production waits add the scheduler queue (waitMs recorded on the build).
- Test Flight timing is read from eval journals (flight.at minus build finishedAt), which includes the eval harness polling; the real portal number may be a few seconds lower.
